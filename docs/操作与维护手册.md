## 3. 日常手动流程

每次只运行一个写入阶段。各阶段产生不同 ID：P1 为输出目录；P2 为附件任务；P3 为分析快照；P5 为预览运行。恢复时使用对应 ID，不混用。

### 3.1 先查看已有记录

```powershell
pnpm run assistant results --limit 5
pnpm run assistant queue --limit 5
pnpm run assistant notify --status
```

默认选择最近创建的正式 P3 快照，不是实时网站结果。需看历史日期和 `sourceReport`；没有快照不等于搜索结果为零。诊断需显式指定：

```powershell
pnpm run assistant results --purpose diagnostic --limit 5
```

读取清单时分别看候选、已分析、pending、相关性、公告阶段、正文/附件完整性与资格结论。`review` 与 `pending` 是不同维度，数量不能简单相加。队列只列出正文完整且规则未排除的待分析项，`deferred` 仍需补证据，不表示已排除。

### 3.2 发起新一次正式采集

```powershell
pnpm run assistant collect
```

使用当前“网站开发、广东、最近 7 个自然日”基线。默认两站，每站最多 20 个详情样本；需要单站可用 `collect --site ccgp` 或 `collect --site guangdong`。降低页数/详情上限会缩小覆盖，不代表完整验证。程序打开专用有头浏览器，结束后关闭。

保留返回的 P1 `report.json` 路径，先检查 `status / queries / details / errors / p1AcceptanceComplete`。遇 429、登录或取消，先读进度和错误；P1 没有 resume，重跑是新窗口新任务。不能因采集不完整而擅自扩大关键词或高频重试。

### 3.3 显式归档选定附件

以下为模板，尖括号必须替换为本次报告中真实路径或 ID；不要把示例当作已经执行的任务。

```text
pnpm run assistant archive --report "<P1报告绝对路径>" --pick "<公告ID>:<附件序号>"
pnpm run assistant archive --resume <P2任务ID>
```

附件序号从 **0** 开始，可重复 `--pick`。检查 P1 详情中的实际附件列表，不能按标题猜序号。选择完成后保留 P2 ID 与 `report.json`，逐项检查下载、解析、来源和错误；链接为空不等于原网站没有附件。

重复 `--resume` 校验后复用成功对象。确需重新下载同一链接检查变化时才加 `--refresh`；过期签名链接不会自动更新，应回到真实公告取得当前链接。

### 3.4 生成证据包，再由会话分析

```text
pnpm run assistant analyze --prepare --report "<P1报告绝对路径>"
pnpm run assistant analyze --prepare --report "<P1报告绝对路径>" --archive-job <P2任务ID>
pnpm run assistant queue --run <P3任务ID> --limit 5
pnpm run assistant packet --run <P3任务ID> --packet <证据包ID> --offset 0 --limit 3
pnpm run assistant analyze --run <P3任务ID> --import "<模型结果JSON绝对路径>"
pnpm run assistant results --run <P3任务ID> --limit 5
```

两条 prepare 是有/无 P2 归档的替代方案，选适用的一条。`--previous <旧P3-ID>` 可携带同用途历史；`--track <site:id>` 可显式跟踪已有公告关联的项目，不能代替采集遗漏的更新。正式和诊断不得混用；读取诊断 `queue/packet/results` 均加 `--purpose diagnostic`。

Codex 读取 packet 第一页的提示词、版本与字段规范，并按 `nextOffset` 继续读取所需证据。未读附件应列明限制。将模型 JSON 保存到运行数据根的 `runs/<P3-ID>/session-output/`，保留 `packetId/inputHash/ruleVersion/promptVersion/companyVersion`。来源为 `codex-session`，具体模型标识未知时写 `unknown-exact-model`，不猜测。

命令自身不调用模型。引用/版本错误应修正后重新导入，不手改 `latest` 指针或跳过校验；数组导入可能部分成功，保留已成功项。真实公司输入仍未开放。导出文件需要刷新时：

```text
pnpm run assistant analyze --run <P3任务ID> --render
pnpm run assistant analyze --run <P3任务ID> --evaluate "<人工标签JSON绝对路径>"
```

标签模板在对应 P3 目录中；评估前需要真实人工标注和确认样本范围，不能把合成标签写成业务验收。详见 [P3 记录](D:/creator/coding_project/tender-assistant/docs/P3-过滤去重与AI分析.md)。

### 3.5 生成与查看通知预览

```powershell
pnpm run assistant notify --preview
pnpm run assistant notify --status
pnpm run assistant notify --verify
```

固定输入加 `--run <P3-ID>`，诊断加 `--purpose diagnostic`。返回 P5 ID 和 Markdown 路径。预览包含历史采集问题或分析缺口时，仍以原运行日期为准；它不重新采集。重复事件复用，`previewed` 不代表已外发。当前设置外发或调度开关为 true 会被拒绝，不能通过改开关获得尚未实现的渠道。

## 4. 登录、取消与人工补文件

当前会话来源 ID 在 [config/p2.json](D:/creator/coding_project/tender-assistant/config/p2.json) 中，仅 `ccgp-download` 和 `gdgpo`。其来源登记不代表已确认存在可用登录页；先依据真实附件确定是否需要认证，不能任选一个冒充门户登录。

在带交互终端的环境执行以下模板。程序打开专用浏览器，用户完成必要登录后回终端输入 `done`，取消则输入 `cancel`。不得让助手在未完成登录时代填 done。

```text
pnpm run assistant archive --auth <来源ID> --account <账号别名>
pnpm run assistant archive --resume <P2任务ID> --session <来源ID> --account <同一账号别名>
pnpm run assistant archive --resume <P2任务ID> --item <附件任务ID> --session <来源ID> --account <账号别名> --manual-download
pnpm run assistant archive --resume <P2任务ID> --item <附件任务ID> --import-file "<本地真实文件>"
```

账号别名不是账号密码。持久化会话仅用于同 origin，跨来源单点登录、CA/UKey 仍需现场验证。人工浏览器下载可能选错文件，程序会标为来源待复核；恢复、缓存复用及备份恢复不会解除该限制。核对公告、文件名和内容后，用上述显式 `--import-file` 导入核验文件，保留新观察；报名、购买、签署不是普通下载操作。

运行中按 Ctrl+C 取消，等当前阶段退出并关闭其创建的浏览器。不要删除正在使用的锁或结束无关进程。P2/P5 可按 ID 恢复，P3 可继续导入剩余结果；P1 只能保留证据后重新发起采集。模型调用入口暂无后台连续任务。

## 5. 故障处理速查

| 现象 | 先看哪里 | 处理与成功判据 |
|---|---|---|
| 正式零结果 | P1 查询条件、日期、地区和终止依据 | 查询完整才算零结果；保留原条件，不自动改词 |
| HTTP 403/429、验证码 | P1 errors/progress 与页面证据 | 停止该站，确认站点恢复与访问条件后再低频运行；不循环重试 |
| 只有标题、未知路由、正文缺失 | P1 detail 的完整性与页面证据 | 补站点适配或人工材料；保持 partial/failed，不交给模型补造 |
| 假 PDF、认证页或新下载来源 | P2 条目 reason、来源登记 | 确认真实来源与权限；必要时人工会话/下载，恢复后核对文件类型 |
| 附件 needs-ocr/加密/不支持 | P2 parseStatus 与缺口 | 留待人工可读文件；不宣称全文已解析 |
| 运行锁被占用 | 原命令、archive.lock PID 与任务状态 | 等原进程结束；程序在 SQLite 互斥内处理死 PID 标记。archive.lock.sqlite 常驻不等于占用，不删除该文件，不混跑新旧程序 |
| 无快照或用途不符 | results 的 status/purpose | 先 prepare，或选择正确用途；不回退诊断伪装正式 |
| 指纹、版本、引文校验失败 | 原包、schema、固定错误码 | 保留旧文件，修正输入或重新 prepare；不放宽校验 |
| 预览失败 | P5 回执与尝试次数 | `notify --resume <P5-ID>`；仅恢复 pending/failed，上限 3 次 |
| writing/unknown 或文件冲突 | 通知 ID 与实际预览文件 | 先 `notify --reconcile <通知ID>`；匹配才成功，缺失转失败后恢复，冲突保持未知 |
| 本地账本损坏 | 原文件、备份清单与校验结果 | 停止继续写入，保留证据，在新目录恢复；不清空重建掩盖问题 |

统一入口保持阶段退出码：P1/P2/P5 的 `0` 是本次动作完成，`2` 是部分完成或待处理，`130` 是取消/时限，输入启动错误为 `1`；P3 输入/校验错误为 `1`。`doctor` 未就绪可返回 `2`。退出 0 不代表阶段或业务验收通过。`notify --verify` 还应核对 `unresolved=0`，不能只看 `ok`。

## 6. 备份、恢复与迁移

关键分析导入后、版本更新前和交接前进行核验与备份；本项目没有定时备份。常用命令：

```powershell
pnpm run assistant archive --verify
pnpm run assistant notify --verify
pnpm run assistant notify --backup
```

备份需要两个核验均可解释，`unresolved` 应为 0；有未解决项时先处理或明确记录。`notify --backup` 校验回执后复用归档备份，不替代人工检查正文质量。

备份生成 SQLite 一致副本及 `objects/parsed/notices/runs` 的 SHA-256 清单；不包含登录会话、锁、`.partial` 文件、源码或 P1 网页证据。必须另行保留与快照关联的 `output/playwright/<P1运行目录>/` 全部文件，而不是仅保存 report.json；源码按 Git/受控副本保留。P1 路径受本机目录绑定，未做自动重定位。

恢复演练模板：

```text
pnpm run assistant archive --restore-check "<备份目录绝对路径>"
```

命令会返回新的 `restore-checks/check-*` 目录及 P2 校验结果，不切换当前数据根。还需核对新目录中的 P3 快照和 P5 账本/回执。当前 CLI 没有 `notify --verify --root` 参数，可在项目根使用实际已编译的校验函数检查恢复副本；下面读取恢复目录，不自动成为生产数据：

```powershell
$env:TENDER_RESTORE_CHECK = 'C:\Users\14629\AppData\Local\TenderAssistant\restore-checks\check-1790207989669'
node --input-type=module -e 'import {verifyNotifications} from "./dist/src/notify/verify.js"; const r=await verifyNotifications(process.env.TENDER_RESTORE_CHECK); console.log(JSON.stringify(r)); if(!r.ok||r.unresolved) process.exitCode=2;'
Remove-Item Env:\TENDER_RESTORE_CHECK
```

上例是本机 P5 历史演练目录，其他恢复应替换为命令真实返回的目录。只删除临时环境变量，不删除文件。P6 已重验该副本，当前账本与副本一致；这不是本轮新备份或异机恢复。

若要正式切换数据或迁移机器，先保留当前完整副本，恢复到全新目录，核对 P1 原证据路径、P3 版本、P5 去重和权限后再单独切换配置。不能直接改带指纹的 snapshot 来重写路径。迁移源码后也需重新处理技能绑定；安装器不会强制接管旧项目所有权。**一键搬家、异机恢复和异地备份未验证**，不提供覆盖现有库的快捷命令。

全部材料保留到人工验收，不自动清理。备份和 restore-checks 会持续占磁盘，同盘副本不能应对整盘丢失。确定异地位置和保留策略后再开展备份迁移；不要把 private/sessions 随便打包分发。

## 7. 更新、卸载与回滚

| 变动 | 操作原则 | 复核重点 |
|---|---|---|
| 正式关键词/日期/地区 | 修改已确认配置并同步文档；地区适配目前只支持广东，P3 只接受一个正式关键词 | 页面过滤、范围、规则版本与正式/诊断隔离 |
| 网页改版 | 更新对应 `src/sites/`，保留失败样本 | 受影响解析测试及少量真实站点验证 |
| 提示词/分析规则 | 更新 `prompts/` 或规则代码后重新 prepare | 新版本与引用校验，人工标注效果，旧结果不能冒用 |
| 依赖/浏览器 | 有目的地更新锁文件，先备份与测试 | TypeScript、归档解析、有头会话及站点行为 |
| 技能 | 修改项目内源包并通过安装器更新 | 文件指纹、项目绑定、显式调用与宿主列表 |

代码更新后的基础检查为 `pnpm run check`、`pnpm test`、`git diff --check`；类型构建已包含在 pnpm test 中。真实浏览器/站点只按改动范围验证，并标明采样时间。生成的 dist 不手改，测试用合成数据，不污染真实归档。

只卸载技能的命令如下；它保留源码、附件、数据库和分析结果，不注销政府网站账号。安装副本被手改或出现额外文件时会拒绝，先保留并核验这些修改。

```powershell
& ./integrations/codex/install-skill.ps1 -Uninstall
```

P6 当次交接只新增和更新文档。2026-09-24 后续修复会在新版首次打开归档时迁移 schema 1→2，包括会打开数据库的校验/备份命令；P5 下次保存账本时写 v2。升级前先停止相关任务，使用旧版备份并保留关联 P1 证据。回滚旧代码需配套升级前完整备份，恢复到新目录核验，不能强改版本号或覆盖现用数据；升级后新记录应另行保留。当前无外部发送和周期任务。

历史分析包、已导入结论和预览不会自动修订；新通知会从正文重算临期日期。修订旧 DOCX 解析时，先核对原文件，显式导入或 `--refresh` 重新解析，再重新 prepare/分析；缓存复用不会重解析。旧 Bug 已覆盖且无法追溯的人工来源复核状态需人工核查，不能把升级成功等同于全部历史材料已修正。

维护责任建议：业务负责人确认规则、标签、公司证据和验收范围；使用人员处理登录、人工复核与异常反馈；开发维护人员处理站点适配、数据恢复和版本升级。实际负责人尚未指定，不在文档中代签。
